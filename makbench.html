The read

Why trials matter — the numbers move

At 1 trial the two agents look level on most models, with ZeptoClaw ahead on Nemotron. Run each task 5 times and the picture sharpens: Sonnet 5 firms up 0.80 → 0.92 pass@1 (its lone single-run miss was variance), while Nemotron's lucky 0.80 corrects to 0.64 — and its pass^5 of 0.50 reveals only half its tasks pass all five times. GPT-5.6 sol and Gemini 3.5 Flash are perfectly reliable (pass^5 = 1.0). That's the whole point of multiple trials: pass@1 asks "can it?", pass^5 asks "can I rely on it?". Gemma 4 31B lands at 0.82 / pass^5 0.70 — its one hard failure (expense-audit, 0/5) is the 32K-context ceiling of its flat-rate host, not bad luck. These numbers are reproducible and cost-honest — same sandbox, same fixture, every dollar metered. (OpenClaw's 5-trial run is still to land.)

2 · The harness

One agent, one task, one sealed sandbox

MAKBench benchmarks CLAW-style CLI agents — ZeptoClaw, OpenClaw, Aider, Claude Code and the long tail of similar tools — across different LLMs. Each attempts a real task in an isolated Docker sandbox; every LLM call routes through one metered gateway; the finished workspace is graded in a separate, trusted container. Identical starting state and limits make agent/model pairings genuinely comparable — and every dollar of cost is observed, not self-reported.

01
Prepared image
The agent's digest-pinned image, install steps baked in and snapshotted — attempts start in ~1s.
02
Fresh workspace
A new volume, staged with the task fixture, the prompt written to a file, and a git baseline commit.
03
Container launch
A detached container, workspace at /workspace, hard CPU & memory caps.
04
Gateway-only net
Joined to an internal bridge whose only peer is the gateway — no route to the open internet.
05
Supervision
A 1 Hz loop enforces wall-clock, stall and step budgets, then dumps the full log.

Adding an agent is a single YAML file — no code. The universal cli-generic adapter fills in the model and prompt per attempt and points the agent's SDK env vars at the gateway.

agents.d/zeptoclaw.yaml
id: zeptoclaw
adapter: cli-generic
image: ghcr.io/qhkm/zeptoclaw@sha256:e32bce56…b86a   # digest-pinned
command:
  - /bin/sh
  - -c
  - |
    export OPENAI_BASE_URL="$OPENAI_BASE_URL"   # points at the metered gateway
    exec zeptoclaw agent --mode autonomous -m "$(cat {prompt_file})"
env_style: openai

The gateway is the one source of cost truth. Before each attempt it mints a per-attempt, budget-capped virtual key — an agent can't outspend it. Real provider keys never enter the sandbox (the config references env-var names only), and the key's call log — tokens, latency, computed cost — is ingested at the highest gateway provenance.

4 · Verification & scoring

Graded by a container the agent can't touch

Untrusted code does the work; trusted code does the grading. The two never share a process — so a malicious image can, at worst, fail itself.

Phase 1 · agent
Untrusted sandbox
  • Runs in the task image — possibly third-party
  • Reads TOOLS.md, calls tools, writes files
  • Never sees the hidden verify/ tests
Phase 2 · verifier
Trusted grader
  • MAKBench-owned image (git · pytest · curl)
  • Mounts the frozen workspace read-only
  • Grades the resulting state — not how it got there
How crm-pipeline-update scores

Outcome-based. The hidden test_crm.py opens the mutated workspace and asserts two weighted checks; pass_threshold = 1.0 means both must pass.

test_deals_won · 0.4
L-003/007/010 are stage won, dated correctly.
test_pipeline_totals · 0.6
Recomputes from the live DB; compares JSON within ±0.01.

Anti-triviality: a pristine fixture must fail — so a no-op agent scores zero.

The metrics
correctness
Weighted graded fraction of one attempt, 0–1.
pass@1
Share of attempts clearing the threshold.
pass^5
Reliability: share of tasks passing all 5 trials.
cost / success
Spend incl. failures ÷ passes.

Cost bases never blend: metered per_token and amortized flat_rate (shown ~) are different units.
